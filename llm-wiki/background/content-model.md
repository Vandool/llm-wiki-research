# Content model for the LLM-maintained repository wiki

Shared reference for the approach ADRs in `../approaches/`. Whatever executes the update (local hook, GitLab CI, bot service, IDE agent; ADR-01…ADR-10) reads and writes the pages described here. Requirement IDs R1–R8 come from `../requirements.md`; problem IDs P01–P24 and design rules D01–D22 from `problems-and-fixes.md`; landscape facts from `landscape.md`. External sources are numbered [n] in §13; **(opinion)** marks my own design choices.

Scope: the *shape* of the wiki (files, frontmatter, links, sizes, lint), not the update mechanics. Format baseline: Google Cloud's Open Knowledge Format (OKF) v0.2 [2][3], as recommended by ADR-07; every rule below extends OKF and none contradicts it (OKF: producers MAY add keys, consumers MUST NOT reject unknown keys or types [2]).

## 1. Design principles

| # | Principle | In practice | Why (sources, problems) |
|---|---|---|---|
| CM1 | **Agent-first, human-readable** | Plain Markdown + YAML, one topic per file, facts first (what, where, contracts, owner), prose after. No page needs a renderer to be useful. | Karpathy: the LLM owns the wiki layer, humans browse it in Obsidian [1]; OKF "just markdown, just files" [3]; OpenWiki "built for agents, explored by humans" [4]. P12. |
| CM2 | **One fact in one place** | A fact lives on exactly one page (or in one generated artefact) and is linked from everywhere else. Instruction files hold pointers and rules, not knowledge; PO pages link to developer pages instead of restating them. | P13, D11; Karpathy's lint checks "missing cross-references" [1]. |
| CM3 | **Page-to-source traceability** | Every machine-written page lists `sources` (code paths, contract operations, ADRs) and the commit at which they were last checked; load-bearing claims carry OKF footnotes keyed to `sources[].id`. | OKF §5.1 [2]; OpenWiki `repo://path#L-L` sources [4]; DeepWiki "Sources:" lines with line ranges [6]; P01, P02, P22, D01, D12. |
| CM4 | **PO layer separate from developer layer** | `wiki/product/` has its own page types, template, vocabulary contract and CODEOWNERS; it cites *behaviour* (API operations, events, flags), never files. | P14, D20; Diátaxis: keep the four forms distinct, do not blend them in one page [7]. |
| CM5 | **Stable ids and links** | Every page has `id` = `<repo>/<path-without-.md>`; links are file-relative Markdown links; renames keep `aliases`; one canonical cross-repo URL form (§6). | OKF links are untyped and consumers tolerate broken ones [2]; Quartz alias redirects [25]; P23. |
| CM6 | **Bounded page sizes** | Each page type has a line budget (§3); indexes shard; the log rotates. Budgets are enforced by lint (L04), not by prompt. | P03; Agent Skills: SKILL.md < 500 lines, body < 5,000 tokens [13]; D11. |
| CM7 | **Deterministic facts vs narrative** | Anything derivable from files (indexes, contract tables, catalogue, dependency and event maps, changelog skeleton, ownership) is generated by scripts and is read-only for the LLM; the LLM writes narrative pages, and only the sections whose sources changed. | D06, D07, D08; ADR-08's backbone/narrative split; P19, P22. |

## 2. Directory layout

### 2.1 Single repository

The wiki is an OKF bundle rooted at `wiki/`: `index.md` and `log.md` are reserved, every other `.md` file is a concept document with frontmatter [2]. Karpathy's `raw/` layer is the repository itself plus its contract and decision files; the wiki links to them and never copies them [1] (opinion). File and folder names are lowercase kebab-case because Quartz lowercases slugs [22].

Naming note: the brief calls the two navigation files `INDEX.md` and `LOG.md`. OKF reserves the lowercase names `index.md`/`log.md`, an uppercase `INDEX.md` would count as a concept document without `type`, and Quartz lowercases URLs, so the canonical files are `wiki/index.md` and `wiki/log.md`; "INDEX.md" in prose means `wiki/index.md` (decision, not opinion: OKF conformance [2]).

```
<repo>/
├── AGENTS.md                        # ≤120 lines: rules + managed block pointing at wiki/index.md (D10, D11)
├── CLAUDE.md                        # optional: "@AGENTS.md" import (P13)
├── .github/
│   ├── copilot-instructions.md      # shim: same managed block, for surfaces without AGENTS.md support
│   ├── instructions/*.instructions.md   # applyTo-scoped pointers to wiki pages
│   ├── prompts/wiki-update.prompt.md    # the R5 "form" for VS Code / JetBrains users
│   ├── agents/wiki-maintainer.agent.md  # custom agent used by the update job
│   └── skills/wiki-navigate/SKILL.md, wiki-maintain/SKILL.md   # or .agents/skills/ (both read by Copilot)
├── catalog-info.yaml                # service descriptor (Backstage format): owner, provides/consumes APIs, dependsOn
├── api/openapi.yaml, asyncapi.yaml  # contracts = raw sources (human/tool-owned)
├── docs/adr/NNNN-*.md               # MADR decisions = raw sources (human-owned; MADR status vocabulary ≠ OKF's)
├── CHANGELOG.md                     # Keep a Changelog, generated from Conventional Commits
└── wiki/                            # the OKF bundle
    ├── index.md                     # generated; okf_version: "0.2"; lists folder indexes + "start here" pages
    ├── log.md                       # generated, newest first, rotated (§5)
    ├── log/2026-q2.md               # type: Log Archive
    ├── conventions.md               # type: Conventions, human-owned (Karpathy's conventions.md [1])
    ├── overview.md                  # type: Overview
    ├── glossary.md                  # type: Glossary (plain + technical line per term)
    ├── architecture/{index,context,containers,deployment}.md   # C4 L1/L2 + arc42 §3/§5/§7
    ├── modules/index.md, <module>.md            # type: Module — one per container/component
    ├── concepts/index.md, <concept>.md          # type: Concept — explanation
    ├── howto/index.md, <task>.md                # type: How-to — task-shaped
    ├── contracts/index.md
    │   ├── api/<api>.md, events/<channel>.md    # type: Contract — generated from OpenAPI/AsyncAPI
    │   └── <api>-guide.md                       # type: Contract Guide — written
    ├── decisions/index.md                       # generated from docs/adr/
    ├── runbooks/index.md, <alert-or-task>.md    # type: Runbook — human skeleton, agent-appended
    ├── analyses/index.md, <question>.md         # type: Analysis — filed query answers
    ├── product/                                 # PO layer (CM4); CODEOWNERS: product owners
    │   ├── index.md
    │   ├── features/<feature>.md                # type: Feature
    │   ├── capability-map.md                    # generated from Feature frontmatter
    │   ├── release-notes/<version>.md           # type: Release Notes
    │   └── what-changed.md                      # type: What Changed (rolling 30 days)
    └── .manifest.json                           # machine state: page → sources → blob hashes (not a page)
```

### 2.2 Central multi-repo hub

One GitLab project (`platform-wiki`) builds the Quartz site (R8) and owns the cross-repo pages. Repository bundles are copied *unchanged* into `content/repos/<repo>/` at build time; only cross-repo URLs are rewritten (§6). The copies are build artefacts, not commits (opinion; ADR-09 decides the fetch mechanism).

```
platform-wiki/
├── AGENTS.md
├── quartz.config.ts, quartz.layout.ts     # markdownLinkResolution: "relative" (§11)
├── .gitlab-ci.yml                         # aggregate → lint → npx quartz build → pages
├── hub/                                   # committed hub-owned bundle, mounted at the content root
│   ├── index.md                           # site home: catalogue summary + links to repos
│   ├── log.md
│   ├── catalogue/                         # generated: services.md, dependencies.md, events.md, contracts.md, owners.md
│   ├── services/<repo>.md                 # type: Service — generated from catalog-info.yaml + repo overview
│   ├── concepts/                          # cross-cutting concepts (written)
│   ├── decisions/                         # cross-cutting MADR ADRs (human-owned)
│   ├── glossary.md                        # generated union of repo glossaries + conflict list
│   └── product/capability-map.md          # generated union of repo capability maps
├── content/                               # build output only (gitignored): hub/ + repos/<repo>/ ← <repo>/wiki/
├── llms.txt                               # generated from hub/index.md, published at the site root
└── tools/                                 # aggregate.py, rewrite_links.py, lint/, page.schema.json (shared schema, D18)
```

## 3. Page types

`type` values are ours; OKF leaves the registry to producers [2]. Diátaxis names the *kind of writing* [7]; arc42 and C4 name the architecture pages [8][9]. Mapping from the two reference schemas: Karpathy's `overview.md` → Overview, `entities/` → Module and Service, `concepts/` → Concept, `sources/` (one page per raw source) → Contract, `analyses/` → Analysis [1]; DeepWiki's overview → module pages with parent/child relations, diagrams and source-file links (configurable as `pages[].title/purpose/parent` in `.devin/wiki.json`) → Overview → Architecture → Module [5][6]. Owner values: `human` (bot read-only, D09), `agent` (LLM writes, humans review), `process` (script-generated, LLM read-only), `both` (human skeleton, agent-appended sections). Size budgets are (opinion): ≈12 tokens per Markdown line, so a 200-line page is ≈2.5k tokens and a five-page task context stays under ≈15k tokens.

| `type` | Path | Purpose (Diátaxis / arc42) | Audience | Owner | Update trigger | Max size | Required frontmatter beyond base (§4) |
|---|---|---|---|---|---|---|---|
| — (reserved) | `index.md` per folder | Catalogue, progressive disclosure [2] | agent, dev | process | page added, renamed, description changed | 120 lines root, 200 per folder | none (root only: `okf_version`) |
| — (reserved) | `log.md` | Chronology [1][2] | agent, dev | process | every run | 200 entries | none |
| Log Archive | `log/<yyyy>-q<n>.md` | Rotated log | dev | process | rotation | unbounded | `description` (period, counts) |
| Conventions | `conventions.md` | Non-discoverable rules for this repo's wiki [1] | agent, dev | human | manual | 100 | — |
| Overview | `overview.md` | Explanation: what the repo is (arc42 §1, §4) | dev, agent | agent | Module or Architecture change | 150 | `sources` |
| Architecture | `architecture/*.md` | C4 context + container [9], arc42 §3, §5, §7; Mermaid | dev, agent | both | catalog, deps, deployment files change | 200 each | `sources`, `related` |
| Module | `modules/<name>.md` | Reference + explanation for one building block (C4 container/component) | agent, dev | agent | any file under `sources` changes | 200 | `sources` (≥1 `repo://`), `provides`/`consumes` |
| Concept | `concepts/<name>.md` | Explanation of a domain or technical concept | agent, dev | agent | lint gap, ingest | 120 | `sources` |
| How-to | `howto/<task>.md` | Task-oriented procedure ("add an endpoint") | agent, dev | both | commands/config in `sources` change | 120 | `sources` |
| Contract | `contracts/api/*.md`, `contracts/events/*.md` | Reference tables from OpenAPI/AsyncAPI | agent, dev | process | spec file change | 400 (split by tag) | `resource` (spec file), `provides` |
| Contract Guide | `contracts/<api>-guide.md` | Explanation: semantics, versioning, error model | dev, agent | both | Contract page change | 150 | `sources` (`api://`, `event://`) |
| Decision | `docs/adr/*.md` (raw) + `decisions/index.md` | MADR record [11] | dev, agent | human | manual | 100 | MADR keys (`status`, `date`, `decision-makers`) |
| Runbook | `runbooks/<name>.md` | Operations how-to: alert → steps → verify → escalate [12] | dev (on-call), agent | both | alert/config sources change | 150 | `sources`, `team`, `stale_after` |
| Glossary | `glossary.md` | Reference: term → plain line + technical line | po, dev, agent | both | new term detected | 300, then split | — |
| Feature | `product/features/<slug>.md` | PO explanation of one user-visible feature | po | both | behaviour-level sources change; release | 80 | `audience: [po]`, `capability`, `sources` (no `repo://`) |
| Capability Map | `product/capability-map.md` | Reference: capability → features → services | po | process | Feature frontmatter change | 150 | `audience: [po]` |
| Release Notes | `product/release-notes/<version>.md` | PO-readable notes per release | po | both | git tag | 200 | `audience: [po]`, `sources` (`changelog://`) |
| What Changed | `product/what-changed.md` | Rolling "since last release" digest | po | agent | merge touching PO sources | 60 | `audience: [po]` |
| Analysis | `analyses/<question>.md` | Filed answer to a repo question [1] | agent, dev | agent | on query | 200 | `sources` |
| Service (hub) | `hub/services/<repo>.md` | Catalogue entry per repository | agent, dev, po | process | catalog or overview change | 100 | `resource`, `team`, `provides`, `consumes` |

ADR files stay outside the bundle on purpose: MADR's `status` values (`proposed`, `accepted`, `superseded by …`) [11] conflict with OKF's `status` enum [2]; the bundle only carries the generated `decisions/index.md`.

## 4. Frontmatter schema

OKF keys keep OKF semantics [2][3]; extension keys use plain names (OKF permits additional keys and requires consumers to preserve them [2]). Keys marked ✱ are required on every concept page by lint L06; `type` is the only key OKF itself requires.

| Key | Origin | Type | Rationale |
|---|---|---|---|
| `type` ✱ | OKF | string from §3 | Selects template, lint profile and size budget. |
| `title` ✱ | OKF; Quartz, Obsidian | string ≤ 80 chars | Display name; Quartz falls back to the filename otherwise [23]. |
| `description` ✱ | OKF; Quartz | one sentence | Becomes the `index.md` line and the link preview; indexes are generated from it (D06). |
| `resource` | OKF | URI | Canonical asset: GitLab tree URL (Module), spec file (Contract), dashboard (Runbook). |
| `tags` | OKF; Quartz, Obsidian | list of lowercase strings, `/` for hierarchy | Cross-cutting labels; Quartz builds tag pages [24]. |
| `sources` ✱ (agent/process pages) | OKF §5.1 | list of `{id, resource, title?, last_modified?, author?}` | Traceability (CM3). `resource` uses URI schemes: `repo://<path>[#L<a>-L<b>]` (as OpenWiki [4]), `api://<api-id>/<operationId>`, `event://<channel>`, `adr://<NNNN>`, `changelog://<scope>@<from>..<to>`, `flag://<key>`, `https://…`. `id` is the footnote key for per-claim citations [2]. PO pages may not use `repo://` (L07). |
| `generated` ✱ | OKF §5.2 | `{by: actor, at: ISO 8601}` | Who last meaningfully changed the page. Actors follow OKF: `copilot-cli/<model>`, `process:<script>/<ver>`, `human:<gitlab-user>` [2][3]. |
| `verified` | OKF §5.2 | list of `{by, at}` | Trust tier is *derived*: none = unverified, machine only = machine-confirmed, any `human:` = human-reviewed [3]. This replaces the stored `confidence` of D01/D13 (CM2: one fact in one place). |
| `status` | OKF §5.3 | `draft`, `stable`, `deprecated` (absent = stable) | Bootstrap and lint output start as `draft` (D13); the index marks drafts; deprecated pages stay linkable. |
| `stale_after` | OKF §5.5 | ISO 8601 instant | Time-based staleness for pages without hashable sources (Runbook, Feature, Overview); L03 compares dates. Defaults (opinion): Runbook 180 d, Feature 90 d, Overview 180 d. |
| `id` ✱ | ext | `<repo>/<path-without-.md>` | Stable identity for cross-repo links, aliases and the hub manifest (CM5). L06 checks `id` == actual path. |
| `schema_version` ✱ | ext (D01, D18) | integer | Content-model version the page conforms to; migrations bump it. |
| `audience` ✱ | ext (D01, D20) | list of `agent`, `dev`, `po` | Selects lint profile (L07) and site sections. |
| `owner` ✱ | ext (D01, D09) | `human`, `agent`, `process`, `both` | Who may write the page; a bot diff may not touch `human` or `process` pages (L09). |
| `team` | ext | `@group` handle | Human contact, from CODEOWNERS or `catalog-info.yaml`; hub `owners.md` is built from it [30][33]. |
| `last_verified_commit` ✱ (agent/process pages) | ext (= D01 `source_commit`) | 40-hex SHA | Commit at which `sources` were checked against the prose; drives diff-based staleness (D07, L03). |
| `provides`, `consumes` | ext (P23) | lists of `api:<id>`, `event:<channel>` | Vocabulary for the hub dependency and event maps; validated against Contract pages (L12). |
| `related` | ext | list of page ids | "See also" edges for the graph and index; prose links stay the primary edges. |
| `capability` | ext (Feature only) | string | Groups Feature pages into the capability map. |
| `aliases` | Quartz, Obsidian | list of old slugs | Redirects after renames [25]. |

JSON Schema (draft 2020-12 [36]) for the base page, abbreviated; the full file ships in the shared CI component as `tools/page.schema.json` (D18):

```json
{ "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://wiki.example/schema/page/v1", "type": "object",
  "required": ["type","title","description","id","schema_version","audience","owner","generated"],
  "properties": {
    "type": {"enum": ["Conventions","Overview","Architecture","Module","Concept","How-to","Contract","Contract Guide",
                      "Runbook","Glossary","Feature","Capability Map","Release Notes","What Changed","Analysis","Service","Log Archive"]},
    "title": {"type":"string","maxLength":80},
    "description": {"type":"string","maxLength":200},
    "resource": {"type":"string","format":"uri-reference"},
    "tags": {"type":"array","items":{"type":"string","pattern":"^[a-z0-9][a-z0-9/-]*$"}},
    "sources": {"type":"array","items":{"type":"object","required":["id","resource"],
      "properties":{"id":{"type":"string","pattern":"^[a-z0-9-]+$"},
        "resource":{"type":"string","pattern":"^(repo|api|event|adr|changelog|flag|https?)://"},
        "title":{"type":"string"},"last_modified":{"type":"string","format":"date-time"},"author":{"type":"string"}}}},
    "generated": {"type":"object","required":["by","at"],
      "properties":{"by":{"type":"string","pattern":"^(human:|process:)?[A-Za-z0-9._@-]+(/[A-Za-z0-9._-]+)?$"},
                    "at":{"type":"string","format":"date-time"}}},
    "verified": {"type":"array","items":{"type":"object","required":["by","at"]}},
    "status": {"enum":["draft","stable","deprecated"],"default":"stable"},
    "stale_after": {"type":"string","format":"date-time"},
    "id": {"type":"string","pattern":"^[a-z0-9-]+/[a-z0-9/-]+$"},
    "schema_version": {"type":"integer","const":1},
    "audience": {"type":"array","minItems":1,"items":{"enum":["agent","dev","po"]}},
    "owner": {"enum":["human","agent","process","both"]},
    "team": {"type":"string","pattern":"^@"},
    "last_verified_commit": {"type":"string","pattern":"^[0-9a-f]{40}$"},
    "provides": {"type":"array","items":{"type":"string","pattern":"^(api|event):"}},
    "consumes": {"type":"array","items":{"type":"string","pattern":"^(api|event):"}},
    "related": {"type":"array","items":{"type":"string"}},
    "capability": {"type":"string"},
    "aliases": {"type":"array","items":{"type":"string"}}
  },
  "allOf": [
    {"if":{"properties":{"owner":{"enum":["agent","process"]}}},"then":{"required":["sources","last_verified_commit"]}},
    {"if":{"properties":{"audience":{"contains":{"const":"po"}}}},
     "then":{"properties":{"sources":{"items":{"properties":{"resource":{"not":{"pattern":"^repo://"}}}}}}}}
  ] }
```

`verified.by: human:…` and `owner: human` are different facts: the first says a person confirmed the content, the second says only people may edit it.

## 5. Index and log conventions

**`index.md` (Karpathy's catalogue, OKF reserved file).** One `index.md` per folder, generated from frontmatter by a script and never edited by the LLM (D06, P05). OKF body form [2]: sections of `* [Title](file.md) - description`; we append audience and status markers so an agent can skip pages without opening them (opinion):

```markdown
# modules
* [Orders service](orders.md) - Owns the order lifecycle; emits order.* events. [agent,dev]
* [Payments adapter](payments-adapter.md) - Wraps the PSP client; retry policy. [agent,dev] (draft)
```

The root `wiki/index.md` carries `okf_version: "0.2"`, the only frontmatter OKF permits in an index [2], and lists the folder indexes plus at most 20 "start here" pages. Budgets (L04): root ≤ 120 lines, folder index ≤ 200 lines; beyond that the generator shards (`index.md` → `index-a-m.md`, `index-n-z.md`, or by sub-folder) so no file an agent must read exceeds ≈2.5k tokens. Karpathy reports index-first retrieval works to "hundreds of pages" [1]; sharding extends it, and past a few thousand pages a grep/BM25 tool over `title`, `description` and `tags` replaces reading indexes (P03).

**Navigation protocol for agents** (encoded in the `wiki-navigate` skill, §9): (1) read `wiki/index.md`; (2) read the one or two folder indexes matching the task; (3) open at most five pages; (4) follow `sources` into code rather than reading more wiki; (5) do not read `log.md` unless fixing a bug (last 20 entries). Instructions of this shape are followed; overviews dumped into context are not (landscape §7c, P12).

**`log.md` (OKF reserved file).** OKF prescribes date-grouped entries, newest first, no frontmatter, `* **Action**: text` [2]; Karpathy's `## [date] op | title` carries the same information [1], so we adopt the OKF shape and keep Karpathy's operation vocabulary as the bold word: `Bootstrap`, `Creation`, `Update`, `Deprecation`, `Lint`, `Query`, `Instruction` (a human form submission, R5). Entries are only added, never edited; each names the page, the commit range and the MR:

```markdown
## 2026-09-02
* **Update**: [Orders service](modules/orders.md) — sources changed in a1b2c3d..d4e5f6a (MR !412); sections Endpoints, Events rewritten.
* **Instruction**: human:akaveh asked "explain the retry policy for the PO"; filed as [Order retries](product/features/order-retries.md).
```

Rotation and merging (opinion, D06): the script inserts at the top; `log.md` keeps the newest 200 entries, older ones move to `log/<yyyy>-q<n>.md` (`type: Log Archive`; `description` = period and entry counts). Execution models that write from several branches set `wiki/log.md merge=union` in `.gitattributes`; single-writer-on-main models do not need it. The log is a chronology, not a source of facts: no page may cite it (L10).

## 6. Cross-repo linking and the service catalogue

**Link forms.** Markdown links only; no `[[wikilinks]]` (L08), because GitLab's repository file view does not render them ❓ [41] and Quartz's `shortest` resolution becomes ambiguous once many repos share file names [22]. OKF allows bundle-absolute and relative links [2]; we choose *relative* because a bundle copied under `content/repos/<repo>/` then needs no rewriting and GitLab, Obsidian and Quartz all resolve it (opinion; the price is that moves need `aliases`, which L01 enforces).

| Scope | Raw Markdown form | In the merged Quartz site | Notes |
|---|---|---|---|
| Same repo | `[Orders](../modules/orders.md)` — file-relative, keep `.md` | resolved with `markdownLinkResolution: "relative"` [22]; `.md` dropped from the slug ❓ [40] | L01 checks the target exists |
| Code in the same repo | `[handler](https://gitlab.example.com/shop/orders/-/blob/main/src/orders/api.py#L40)` | external link | never a relative path that leaves `wiki/` |
| Page in another repo | `[Payments API](https://gitlab.example.com/shop/payments/-/blob/main/wiki/contracts/api/payments-v2.md)` | aggregator rewrites `…/<repo>/-/blob/<ref>/wiki/<path>.md` → `/repos/<repo>/<path>` | target checked against the hub manifest of page ids (L01) |
| Cross-repo id (frontmatter only) | `related: [payments/contracts/api/payments-v2]` | resolved from the manifest | not for body text |

**Service catalogue.** Facts come from files, not prose (CM7): each repo's `catalog-info.yaml` in Backstage descriptor format [30] (`kind: Component` with `spec.type`, `spec.lifecycle`, `spec.owner`, `spec.providesApis`, `spec.consumesApis`, `spec.dependsOn`; `kind: API` with `spec.type: openapi|asyncapi|graphql|grpc` and `spec.definition`), the `provides`/`consumes` frontmatter of Module and Contract pages, and CODEOWNERS (root, `docs/` or `.gitlab/`, with `[Section]` syntax) [33]. No Backstage server is needed; only the file format is borrowed (ADR-08 makes the same choice). The hub's nightly aggregate job (no LLM) builds:

| Hub page | Built from | Content |
|---|---|---|
| `catalogue/services.md` | all `catalog-info.yaml` + each repo's `overview.md` description | service, type, lifecycle, owner, repo, wiki link, last wiki update, trust-tier counts |
| `catalogue/dependencies.md` | `spec.dependsOn`; `consumesApis` ↔ `providesApis` | Mermaid `flowchart LR` + adjacency table; unresolved references listed |
| `catalogue/events.md` | AsyncAPI `operations` (`action: send` / `receive`) [32] + `provides`/`consumes` | producer → channel → consumers matrix; channels without producer flagged |
| `catalogue/contracts.md` | `kind: API` entities | id, version, owner, consumers, breaking-change log link |
| `catalogue/owners.md` | CODEOWNERS sections + `spec.owner` | team → services → wiki folders |
| `services/<repo>.md` | all of the above | one `type: Service` page per repository |

Contract ids are `api:<catalog API metadata.name>` and `event:<AsyncAPI channel address>`; teams are `@group` handles. Vocabulary drift is caught by L12 at hub lint (P23).

## 7. Contract, API and event documentation placement

Rule: the spec file is the fact; the wiki renders and explains it and never restates it by hand (CM7; P23).

| Artefact | Source of truth (raw layer) | Generated page (`owner: process`) | Written page (`owner: both`) |
|---|---|---|---|

A repository without machine-readable contracts gets a "Contract (unverified ❓)" section on its Module page, and L12 reports the gap so the team adds a spec file rather than prose.

## 8. PO-facing pages

Everything under `wiki/product/` is `audience: [po]`, uses the PO template and is derived from developer pages by *translation*, not by summarising code (P14, D20). Style contract, enforced by L07: no code fences, no file paths, no `repo://` sources, sentences ≤ 25 words, a forbidden-vocabulary list (`endpoint`, `repository`, `MR`, `JSON`, `null`, `exception`, `refactor`, `schema`, `payload`, class and function names), and one "In plain words" paragraph before any table. CODEOWNERS makes the product owners reviewers: `[Product pages] @shop/product-owners` over `/wiki/product/` (enforced approval needs Premium/Ultimate; otherwise the MR template asks for it [33]).

| Page | Derived from | How it is derived and kept non-technical |
|---|---|---|
| Feature (`product/features/<slug>.md`) | Module pages, Contract pages and Guides, CHANGELOG scope | A human writes the skeleton once (what, who, why); the agent maintains "How it behaves" and "What changed recently" from behaviour-level sources (`api://`, `event://`, `flag://`, `changelog://`), so a private refactor never touches the page (ADR-08 §4.9). Required sections: What it does · Who uses it · How it behaves · Limits and known issues · What changed recently (dated bullets, agent-appended) · Related features · For developers (one link to the Module page). |
| Capability map (`product/capability-map.md`) | `capability`, `title`, `description` of all Feature pages; hub union across repos | Generated tree: capability → features → owning service. No prose. |
| Glossary (`glossary.md`) | terms used in Feature, Concept and Contract pages | One entry per term: `**Term** — plain: …; technical: … → [Concept](../concepts/x.md)`. The PO reads the plain line; L07 applies to that line only. The hub merges glossaries and lists conflicting definitions for humans (arc42 §12 [8]). |
| Release notes (`product/release-notes/<version>.md`) | `CHANGELOG.md` grouped by Keep a Changelog types [35] from Conventional Commits [34] | Script builds the skeleton with links to Feature pages; the agent rewrites each bullet as a user-visible outcome ("You can now…", "Fixed: …"); the PO approves via CODEOWNERS. |
| What changed for users (`product/what-changed.md`) | merges since the last tag whose diff touched PO sources | Rolling 30-day digest, ≤ 60 lines, regenerated rather than appended each run; feeds the next release notes. |

The R5 form is also the PO's write channel: "explain order retries for non-developers" is logged as `**Instruction**` and answered as a Feature or Analysis page with `audience: [po]` (Karpathy: file answers back into the wiki [1]).

## 10. Lint rules

Deterministic rules run in CI on every wiki MR and fail it (D03); LLM rules run on a schedule and *propose* an MR (D05, P22). Tools named exist today: lychee (Markdown link checker, `--offline`, `--include-fragments`) [37], gitleaks `dir` mode [38], Vale (`existence`, `substitution`, `metric` rule types) [39], any JSON Schema validator.

| ID | Rule | Kind | How | Severity |
|---|---|---|---|---|
| L01 | Broken links: relative target missing; cross-repo GitLab URL not in the hub page-id manifest; missing anchor | deterministic | lychee `--offline --include-fragments` + manifest lookup | error |
| L02 | Orphan page: no inbound link from a non-index page and not in any `related` (Karpathy lint [1]) | deterministic | link graph | warning; error for Module, Feature |
| L03 | Stale sources: a `repo://` source's blob hash at `HEAD` ≠ the hash in `.manifest.json` for `last_verified_commit`; an `api://`/`event://` subtree hash changed; `stale_after` < today | deterministic detection (D07); the repair is the LLM update | error on `stable`, info on `draft` |
| L04 | Size limits per type (§3); index and log budgets (§5) | deterministic | line and token count | error |
| L05 | Secrets and sensitive strings: gitleaks rules + company deny-list (internal hostnames, customer identifiers) | deterministic | `gitleaks dir wiki/`; regex list | error, blocks merge (D16) |
| L06 | Required frontmatter: schema valid, `id` == path, `type` known, actor strings well-formed, `schema_version` current | deterministic | JSON Schema (§4) | error |
| L07 | Audience leakage on `audience: [po]` pages: forbidden vocabulary, code fences, file paths, `repo://` sources, sentence length, readability metric; plus "would a non-developer understand this?" | deterministic (Vale `existence`, `metric`) + LLM judge (scheduled) | Vale style `po.yml`; the LLM writes a review comment, never edits | error (deterministic) / info (LLM) |
| L08 | Link form: `[[wikilinks]]`, bundle-absolute `/path` links, relative links that leave `wiki/` | deterministic | regex | error |
| L09 | Ownership: bot MR touches `owner: human` or `owner: process` pages, generated blocks, files outside the wiki allow-list (D09), or managed-block markers | deterministic | diff vs base frontmatter | error |
| L10 | Index and log integrity: regenerated `index.md` ≠ committed; log entry does not parse; log cited as a source | deterministic | regenerate and diff | error |
| L11 | Contradictions between pages, and between a page and its sources (Karpathy lint [1]) | LLM, sampled (≤ 20 pages per night), MR with footnoted evidence | `wiki-lint` skill | info |
| L12 | Coverage gaps: catalog component without Module page; spec file without Contract page; `consumes` id with no producer; event with no consumer; Feature without "For developers" link | deterministic | manifest cross-check | warning |
| L13 | Citation coverage: agent page with zero `repo://` sources (D12); load-bearing types (Contract Guide, Runbook, Feature) with paragraphs lacking a footnote; a wiki page cited as a source | deterministic count; claim-level check by LLM | script; `wiki-lint` | error / info |
| L14 | Hidden content: zero-width or tag Unicode, HTML comments other than managed markers, invisible text in pages or instruction files (P09, D14) | deterministic | codepoint scan | error |
| L15 | Duplicated knowledge: heading text shared between a wiki page and `AGENTS.md`/instruction files (P13) | deterministic | heading-set intersection | warning |
| L16 | Trust gate: `status: stable` on Contract Guide, Runbook, Feature, Release Notes requires a `human:` entry in `verified` (D13) | deterministic | frontmatter | error |
| L17 | Churn guard: body changed > 30 % in a bot MR although no source changed (P19, D08) | deterministic | diff ratio | warning |

## 11. Quartz / Obsidian compatibility notes

Checked against the Quartz documentation (the site is labelled v5 ❓; raw docs were read from the `v4` branch of `jackyzha0/quartz`) [22][23][24][25][26][27][28] and Obsidian's properties help [29].

| Topic | Fact | Consequence for this model |
|---|---|---|
| Frontmatter keys Quartz reads | `title`, `description`, `permalink`, `aliases`/`alias`, `tags`/`tag`, `cssclasses`, `draft`, `date`/`created`, `modified`/`lastmod`/`updated`/`last-modified`, `published`/`publishDate`, `socialImage`/`image`/`cover`, `lang`, `comments`, `enableToc` [23] | We use `title`, `description`, `tags`, `aliases` natively. Never reuse `date`, `updated`, `modified`, `lastmod`, `published`, `image`, `cover` for other meanings. `draft` is set only by the aggregator (e.g. to hide `status: draft` PO pages), never by authors. |
| Obsidian defaults | `tags`, `aliases`, `cssclasses` are List properties; types text, list, number, checkbox, date, datetime [29] | `tags` and `aliases` are always YAML lists. Nested objects (`generated`, `sources`) appear as raw text in Obsidian's property panel but are preserved ❓. |
| Wikilinks vs Markdown links | Quartz resolves both; wikilinks are case-insensitive and slugs lowercased [22]; Obsidian can write relative Markdown links (`Use [[Wikilinks]]` off, link format "relative path to file") [28] | Markdown links only (L08); if the vault is the repo, commit `.obsidian/app.json` with those settings. |
| Link resolution | CrawlLinks `markdownLinkResolution`: `absolute` (from content root), `relative` (from the file), `shortest` (file name; full path when ambiguous) [22] | Hub uses `relative`. `shortest` would silently pick the wrong `overview.md` among repos; `absolute` would need rewriting because bundles mount at `repos/<repo>/`. |
| Folder index pages | `index.md` in a folder becomes the folder page; `title` frontmatter is honoured; without one the default "Folder: name" appears [24] | OKF forbids frontmatter in non-root `index.md` [2], so the aggregator injects `title` into the *site copy* only. |
| Tags | tag pages at `/tags/<tag>`, hierarchical with `/`, global `/tags` [24] | Tags are site-wide across repos: shared tags (`po`, `runbook`, `contract`) are deliberate; local ones are prefixed (`orders/legacy`). |
| Aliases | AliasRedirects emits an HTML redirect per alias; no options [25] | Aliases must be unique site-wide; hub lint reports collisions. |
| Mermaid | rendered from ` ```mermaid ` fences by ObsidianFlavoredMarkdown (`enableMermaid`); plugin order matters [26]; Mermaid's C4 diagrams are experimental [10] | Architecture pages use Mermaid `flowchart` or `C4Container`; no image files in the bundle. |
| Home page and slugs | `content/index.md` is the home page [23]; URLs are lowercased [22] | `hub/index.md` mounts there; repo roots become folder pages; file names are lowercase kebab-case and `id` equals the slug. |
| GitLab Pages | Quartz documents a `.gitlab-ci.yml` (`node` image, `npx quartz build`, `public/` artefact); Pages are private to members by default [27] | PO access needs project membership or a public Pages setting (D16 says access-controlled). |
| What breaks in a merged site | same file names across repos under `shortest`; `permalink` or alias collisions; bundle-absolute `/…` links; relative links out of `wiki/`; `.md` links if the extension were not stripped ❓ [40]; oversized tag pages when every repo uses `tags: [service]`; one repo's drafts leaking into the PO section; lowercase slug collisions (`Orders.md` vs `orders.md`) | All caught by L01, L08 and hub lint; the aggregator skips a bundle whose lint fails instead of breaking the site (D18). |

# Transactional outbox

**Problem.** Writing the order and publishing `order.created` to two systems can lose or duplicate events.
**Solution here.** The service inserts the event into `orders_outbox` in the same transaction; a relay polls every 500 ms, publishes to the broker and marks rows sent.[^outbox] Chosen over CDC for operational simplicity.[^adr-12]
**Consequences.** At-least-once delivery: consumers must be idempotent on `event_id` (see [order.created](../contracts/events/order-created.md)).
**Where to look.** Relay loop and retry policy: `src/orders/outbox.py`.
