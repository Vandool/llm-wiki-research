# Repository wiki maintained by Copilot: decision document

Date: 2026-09-02. Owner: Arvand Kaveh. Status: design proposed; two fifteen-minute checks before building.

This is the consolidated outcome of the research pass. The individual ADRs in `approaches/` are evidence; this
document is what to act on. Section 9 lists the GitHub and Quartz documentation pages every claim below was checked
against on 2026-09-02.

## 1. What we are building

Every repository carries its wiki as one folder, `wiki/`, of markdown pages in Google Cloud's Open Knowledge
Format (OKF). Deterministic scripts generate the factual pages (APIs, events, catalogue, dependencies, changelog,
decisions index). GitHub Copilot CLI, running on the developer's machine under the developer's own seat, writes
and maintains the narrative pages, and only those whose declared sources changed in the triggering commit. A git
hook starts the run after each commit in the background; the developer is never blocked. The agent verifies its
own work through Copilot CLI hooks (writes outside `wiki/` are denied before they happen; lint and backlink checks
run before the agent is allowed to stop). GitLab CI never calls a model: it re-runs the same deterministic checks
as a gate on merge requests and builds the multi-repo Quartz site on GitLab Pages. Humans steer through a
request file in the wiki, a one-line command, and optionally a GitLab issue form.

```
developer machine (own Copilot seat)                  GitLab (no model anywhere)
──────────────────────────────────────                ─────────────────────────────────────────
git commit ─► post-commit hook (background)           MR ─► wiki:verify  (same scripts: facts
   copilot -p --agent wiki-maintainer                         regenerated + diffed, lint, staleness,
     │ skill scripts: affected pages, regenerate               backlinks, secrets) ─► blocks if stale
     │   facts, prompt only for listed pages           merge to main ─► trigger hub
     │ hooks: preToolUse denies writes outside wiki/        wiki-hub ─► sparse-clone every wiki/
     │        agentStop blocks until lint + backlinks pass           ─► cross-repo pages (generated)
     └ commit "docs(wiki): …"  [never blocks the dev]                ─► Quartz ─► GitLab Pages
steer: wiki/requests.md · copilot wiki-update "…" · glab issue (optional form)
```

## 3. Cross-cutting decisions

| Decision | Choice |
|----------|--------|
| Page format | OKF v0.2. Reserved `index.md` and `log.md` are generated by scripts, never by the model. Frontmatter: OKF keys `type`, `title`, `description`, `sources[]`, `generated`, `verified`, `status`, `stale_after`, plus `audience`, `owner`, `last_verified_commit`. |
| Facts vs narrative | Generated deterministically: API routers and endpoints, events, service catalogue, dependency graph, changelog, ownership, decisions index, symbol index. Written by the model: overview, architecture narrative, module and concept pages, how-tos, runbook prose, PO pages. |
| Traceability | Every model-maintained page declares `sources`. `wiki/.manifest.json` stores blob and symbol hashes per page. Stale means a declared source's hash changed. No `sources` means human-owned: link-checked only, never rewritten. |
| Links | File-relative markdown links with the `.md` extension. The hub builds Quartz with `markdownLinkResolution: relative`, which Quartz documents as "path relative to the file you are linking from", so the same links work in the repo, in GitLab's file viewer, and on the merged site. Cross-repo links are full GitLab URLs that the hub rewrites. This closes the conflict between the content model and ADR-09; no spike needed. |
| Copilot files | Only Copilot's predefined locations under `.github/` (section 4.1). Nothing else is added to the repository root except `wiki/`. |
| Publishing | One `wiki-hub` GitLab project sparse-clones every repo's `wiki/` with the CI job token, generates the cross-repo pages, builds Quartz v5, publishes to GitLab Pages with access control. Free tier. |

## 4. The design

### 4.1 Per-repository layout, contained

Everything Copilot-related sits in the locations GitHub documents for it. The scripts live inside the skill
directory, which GitHub describes as the place for bundled resources: "Copilot automatically discovers all of
the files in the skill's directory and makes them available alongside the skill's instructions."

```
repo/
├── .github/
│   ├── copilot-instructions.md                 # repo-wide rules; supported in CLI, VS Code, JetBrains, github.com
│   ├── instructions/
│   │   ├── wiki.instructions.md                #   applyTo: "wiki/**"   rules for editing wiki pages
│   │   └── api.instructions.md                 #   applyTo: "src/**/routers/**,src/**/api/**"  → read wiki/api first
│   ├── agents/wiki-maintainer.agent.md         # non-interactive agent profile (tools: read, edit, execute)
│   ├── skills/wiki-maintain/
│   │   ├── SKILL.md                            # the procedure the agent follows
│   │   └── scripts/                            # deterministic, no model: affected.py, facts.py, lint.py,
│   │                                           #   backlinks.py, index.py, manifest.py, requests.py
│   └── hooks/wiki-guard.json                   # preToolUse deny outside wiki/; postToolUse lint the written file;
│                                               #   agentStop block until lint + backlinks pass
├── .pre-commit-config.yaml                     # post-commit (background run), pre-push (staleness report)
│                                               #   hooks come from platform/wiki-hooks; nothing vendored
├── .gitattributes                              # wiki/log.md merge=union
├── .gitlab-ci.yml                              # include: component platform/wiki-ci/verify@x.y
└── wiki/                                       # the OKF bundle
    ├── index.md  log.md  conventions.md  requests.md  .manifest.json
    ├── overview.md  glossary.md  catalog.yaml   # catalog.yaml: owner, provides, consumes, depends_on
    ├── architecture/                            # context, containers, deployment (C4 L1/L2)
    ├── api/                                     # routers and endpoints, generated + written guides
    │   ├── index.md                             #   endpoint table across routers
    │   ├── <router>.md                          #   one page per router: routes, handlers, schemas, auth, errors
    │   └── <router>-guide.md                    #   written: intent, flows, gotchas
    ├── events/                                  # channels and payloads (AsyncAPI or code-derived)
    ├── modules/  concepts/  howto/  runbooks/
    ├── decisions/index.md                       # generated index of the repo's ADRs (wherever they live)
    ├── generated/                               # catalogue, dependency graph, changelog, owners, symbols.json
    └── product/                                 # PO layer: features, capability map, release notes, what changed
```

Root `AGENTS.md` is deliberately absent. Copilot CLI reads `.github/copilot-instructions.md` directly, and GitHub's
matrix shows that file supported in every surface including JetBrains chat and agent, whereas `AGENTS.md` is not
read by JetBrains chat. Add a root `AGENTS.md` only when a non-Copilot agent arrives; the standard fixes its
location at the root, and it can then contain a single line pointing at `.github/copilot-instructions.md`.

### 4.2 The `api/` section

Contracts are generated, not written:

| Stack | Source of truth | Generator |
|-------|-----------------|-----------|
| FastAPI, NestJS with Swagger, any framework that exports OpenAPI | the exported OpenAPI document | one page per tag or router from the spec; `oasdiff` changelog |
| Express, Koa, plain Flask, Django | route registry introspection | a script that lists routes, methods, handler symbols and schemas from the running app or the AST |
| Events | AsyncAPI document, or emitter/consumer symbols from `symbols.json` | one page per channel |
| GraphQL, gRPC | schema, proto files | `graphql-markdown`, `protoc-gen-doc` |

The model writes only the guide page next to each router page and may not edit the generated page.

### 4.3 One update run (the only place the model is called)

`copilot -p "…" --agent wiki-maintainer --model <pinned> -s --no-ask-user --add-dir wiki`, started by the
post-commit hook or by hand. The agent loads the `wiki-maintain` skill and:

1. Runs `scripts/affected.py`: diff since `.manifest.json`'s commit, intersected with every page's `sources`, plus OPEN lines from `wiki/requests.md` and any instruction passed on the command line. Nothing affected and nothing open: the script advances the checkpoint and the agent stops without reading anything else.
2. Runs `scripts/facts.py`: regenerates `api/`, `events/`, `generated/`, `decisions/index.md`. Seconds, no model tokens beyond the tool call.
3. Stops if more than `WIKI_MAX_PAGES` (start at 8) narrative pages are affected, logging "deferred" and telling the developer to run the command by hand, which lifts the cap. A large refactor never runs unattended on a laptop.
4. Edits only the listed pages, reading their declared sources and diff hunks. Request text is passed inside a delimited untrusted block; commit messages are never passed.
5. Runs `scripts/index.py` and `scripts/manifest.py`, then commits with `git add wiki && git commit -- wiki` and the trailer `Wiki-Update: auto`.

Verification is enforced by Copilot CLI hooks, which GitHub documents as follows:

| Hook | Documented capability | Used for |
|------|-----------------------|----------|
| `preToolUse` | returns `permissionDecision: allow / deny / ask` with `permissionDecisionReason`, may return `modifiedArgs`; non-zero exit is fail-closed | deny any write whose path is outside `wiki/`, or targets `index.md`, `log.md`, `generated/`, `api/<router>.md`, or a page with `owner: human` |
| `postToolUse` | may return `additionalContext` appended to the tool output | after each write: run `lint.py` on that file and feed the errors back to the agent |
| `agentStop` | returns `decision: block` with `reason`, which forces another agent turn | run `lint.py` and `backlinks.py` on the whole bundle; block with the error list until clean, with a retry counter that gives up after 3 |

This is what makes the run safe without any CI token: the confinement and the checks happen inside the session.

Loop prevention in the git hook: exit when the worker's environment flag is set, when HEAD carries the trailer,
when the commit touches only `wiki/`, or when the lock directory exists.

### 4.4 Triggers

| Trigger | Runs | Blocks the developer |
|---------|------|----------------------|
| `post-commit` | the run above, in the background | no |
| `pre-push` | `affected.py` only: prints how stale the wiki is; blocks only with `WIKI_STRICT=1` | optional |
| `copilot wiki-update "instruction"` (a shell alias for the same command with the cap lifted) | the run, foreground | by choice |
| GitLab CI `wiki:verify` on every MR | `facts.py` regenerate and diff, `lint.py`, `backlinks.py`, staleness against the manifest, secrets scan. Fails with "run wiki-update" when stale. | gate on merge |
| GitLab CI on main | triggers the hub build | no |

The CI job is the backstop for bypassed hooks (`--no-verify`, an IDE with hooks disabled, a fresh clone before
`pre-commit install`). A bypass delays the update to the next run; `main` cannot go stale silently.

### 4.5 Steering, no tokens

| Channel | Who | Mechanism |
|---------|-----|-----------|
| `wiki/requests.md` | anyone with write access, including the PO through GitLab's single-file editor | the next run consumes OPEN lines, moves them to DONE, logs them |
| `copilot wiki-update "focus on the payments router"` | developers | instruction passed as data to the same run |
| retry | anyone: reopen the request line; developers: run the command | |
| GitLab issue template "Wiki request" (optional) | PO, support | a GitLab issue description template renders as a form: page or topic, audience, what is wrong. A developer runs `copilot wiki-update --issue 123`; the script reads the issue with `glab issue view`, which uses the developer's existing GitLab login, and comments the result link back with `glab issue note`. No extra token. |

The issue template is the literal "form" for people who never touch git. Drop it if the request file is enough.

### 4.6 Publishing and cross-repo

`wiki-hub` keeps `repos.yaml` (project path, slug, branch). Its pipeline sparse-clones each repo's `wiki/` with
`CI_JOB_TOKEN` (each repo allowlists the hub under job token permissions), runs the shared lint, generates the
cross-repo pages from every `wiki/catalog.yaml` and `api/` frontmatter (services, contracts, events, owners,
stale report, `llms.txt`), and builds Quartz v5 into Pages. Repos trigger the hub on merge to main with a
multi-project `trigger:` job from a shared CI/CD component; a nightly schedule is the backstop. Quartz has one
content root, so aggregation is a copy into `content/<slug>/`.

### 4.7 Bootstrap

`copilot wiki-update --bootstrap` on one developer's machine: `facts.py` first, then the model per module
cluster in dependency order (leaves before overviews), one commit per cluster so a failed run resumes. The
developer reviews `overview.md`, `glossary.md` and `product/`, then the manifest checkpoint is set and the hook
takes over. Cost estimate in section 6.

### 4.8 Engine option: OpenWiki

LangChain's OpenWiki runs on the developer machine with its `copilot` provider, which uses the developer's
`gh auth login` session rather than a key, so it passes the no-key test. It brings page planning, grounded claims
with line-range evidence, incremental `--update` and OKF output. Against it: 12x cost variance between identical
runs with no budget flag, a single maintainer, GitHub Actions files written into GitLab repos, and the fact that
it is a third-party client on GitHub's Copilot API, on which GitHub's terms are silent. Treat it as an optional
one-day trial for the bootstrap of large legacy repositories, not as the maintenance engine.

### 4.9 Future autonomous agents

They run the same skill, scripts and hooks under their own identity; the CI gate treats their merge requests like
anyone else's. If a non-human Copilot identity ever exists, the same command runs in a CI job with no other change.

## 5. Risks that remain

| Risk | Cover |
|------|-------|
| prompt injection through requests, issues, third-party code | untrusted block, sanitiser, `preToolUse` deny list, no network tools, CI verify |
| drift | manifest staleness, `agentStop` gate, CI gate on every MR, nightly hub stale report |
| hallucinated identifiers | facts are generated; `lint.py` checks that identifiers in prose exist in `symbols.json` or the API pages |
| model destroys human edits | `owner: human` and generated pages are denied in `preToolUse`; `log.md` union-merges |
| cost | page cap, cheap pinned model, no-op when nothing changed, budget controls at user level in GitHub billing |
| hook bypass | CI gate; a bypass delays, never breaks |
| JetBrains gaps | irrelevant to the pipeline: the executor is the CLI, where instructions, agents, skills and hooks are all marked supported. In JetBrains itself, instructions, agents and skills are preview and hooks are unsupported; that affects only interactive use. |

## 6. Cost, computed from GitHub's price list

GitHub bills Copilot usage per token in AI credits, one credit being $0.01. Copilot Business includes 1,900
credits per user per month, pooled across the organisation; usage beyond the pool costs $0.01 per credit, and
budgets can be set per user. Documented per-million-token prices used below: GPT-5 mini $0.25 in / $2.00 out,
Claude Haiku 4.5 $1.00 / $5.00, Claude Sonnet 4.6 $3.00 / $15.00.

Assumptions to confirm in the pilot: an incremental run reads about 60k tokens and writes 4k; a bootstrap
cluster reads about 150k and writes 15k.

| Model | Credits per incremental run | 20 runs per developer per month | Bootstrap, 40 clusters |
|-------|-----------------------------|----------------------------------|------------------------|
| GPT-5 mini | 2.3 | 46 of 1,900 | 270 |
| Claude Haiku 4.5 | 8 | 160 of 1,900 | 900 |
| Claude Sonnet 4.6 | 24 | 480 of 1,900 | 2,700 |

Pin the small model for incremental runs; use a larger one only for bootstrap if quality demands it.

## 7. Checks before building, fifteen minutes each

The earlier spike list is withdrawn. Confinement, hook capabilities, file locations, surface support, link
resolution and pricing are all documented and are cited in section 9. Latency does not need measuring because the
hook runs in the background. Two things are specific to your environment and cannot be read from a document:

1. On one developer machine, under the company's GitHub login (use `copilot login --host` if the enterprise is on data residency), run `copilot -p "say ok" --agent wiki-maintainer -s --no-ask-user`. Confirms the org policy has the CLI enabled, the pinned model is allowed, and programmatic mode authenticates under your login.
2. With `hooks/wiki-guard.json` in place, ask the agent to write `README.md`. Confirms the deny hook fires and shows the exact `toolName` and `toolArgs` field names for write calls in your CLI version, which the script matches on.

Optional, one day, only if wanted: the OpenWiki bootstrap trial from section 4.8.
